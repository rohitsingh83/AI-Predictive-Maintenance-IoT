# Model Card - AI-Powered Predictive Maintenance

Two models are shipped. Both are produced by `python train_model.py`.

## Model A - AI4I tabular failure classifier (deployment model)

| Item | Value |
|---|---|
| Intended use | Score a machine snapshot (5 sensor channels) and decide whether to schedule maintenance |
| Dataset | AI4I 2020 Predictive Maintenance (UCI), 10,000 rows, 3.4% failure rate |
| Inputs | 5 raw sensors + 9 engineered physics features + machine type (15 features) |
| Algorithm | RandomForest (300 trees), selected from 4 candidates by 5-fold CV PR-AUC |
| Probability calibration | Isotonic regression |
| Alarm threshold | **0.26** (chosen to minimise expected business cost, not 0.5) |
| Test set | 2,000 held-out rows, 68 real failures |

| Metric (untouched test set) | Value |
|---|---|
| Accuracy | 0.9895 |
| **Recall (failures caught)** | **0.8088** (55/68) |
| **Precision (alarm quality)** | **0.8730** (55/63 alarms real) |
| F1 | 0.8397 |
| ROC-AUC | 0.9782 |
| PR-AUC | 0.8706 |
| Balanced accuracy | 0.9023 |
| MCC | 0.8349 |
| Brier score | 0.0085 |
| Confusion matrix | TP 55 · FP 8 · FN 13 · TN 1924 |

## Model B - virtual-fleet time-series early-warning model

| Item | Value |
|---|---|
| Intended use | Predict a breakdown up to 6 cycles (1 h) in advance from a live sensor stream |
| Dataset | 27,000 samples · 30 machines · 118 breakdowns (generated by `src/simulate_iot_sensors.py`) |
| Evaluation split | **machine-wise** - 24 machines train, 6 machines test (6 never seen) |
| Inputs | 92 features: rolling mean/std/min/max/range/trend over 5 & 15 cycles, deltas, baseline z-scores, composite indices |
| Algorithm | ExtraTrees, selected from 4 candidates by 5-fold CV PR-AUC |
| Alarm threshold | **0.36** (cost-optimised) |

| Metric (unseen machines) | Value |
|---|---|
| Accuracy | 0.9963 |
| Recall | 0.9701 (227/234) |
| Precision | 0.9458 |
| F1 | **0.9578** |
| ROC-AUC | 0.9998 |
| PR-AUC | 0.9951 |
| MCC | 0.9560 |
| Brier | 0.0035 |
| Confusion matrix | TP 227 · FP 13 · FN 7 · TN 5153 |

**Early-warning performance (alert engine, held-out machines):** 100% of 39 breakdowns
flagged before failure · average lead time 5.3 cycles = **0.9 hours** of advance notice.

## Top drivers

* **AI4I:** heat_dissipation_index (18.0%), rotational_speed_rpm (15.2%),
  torque_per_rpm (14.8%), tool_wear_min (12.1%), torque_nm (11.9%), mechanical_power_w (10.4%).
* **Virtual fleet:** temperature_c_mean_5 (18.3%), temperature_c_max_5 (16.3%),
  temperature_c_max_15 (13.7%), temperature_c_min_5 (11.5%), temp_rise_above_ambient (10.2%).

Note how **engineered features dominate raw sensors** - the single most transferable
lesson of this project.

## Limitations & honest caveats

1. Trained on a **public benchmark** plus a **simulated fleet**; a real plant must
   re-train on its own work orders before trusting the numbers.
2. Classifies "failure within the horizon" - it is **not** a remaining-useful-life (RUL)
   regressor. Adding RUL is the natural next step.
3. The simulator encodes specific degradation physics; real failure modes are noisier and
   include human error, which no sensor captures.
4. No data-drift monitoring in the demo. In production, watch input distributions and
   re-calibrate sensors - a drifting sensor looks exactly like a failing machine.
5. Cost constants ($4,500/h downtime, $400 repair) are illustrative; replace them with
   your plant's real figures (the code reads them from `src/config.py`).

## Ethical / safety notes

* The system **assists** maintenance engineers; it must not silently override safety
  interlocks or permit unattended operation of dangerous machinery.
* A false negative is a safety risk, which is why the threshold is weighted toward
  recall, and why CRITICAL alerts recommend a physical stop-and-inspect.
